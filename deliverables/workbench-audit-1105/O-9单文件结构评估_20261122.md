## 二、为什么单文件是刻意设计，不是技术债失控

1. **便携性是产品前提**：`~/Documents/Obsidian Vault/Projects/*.html` 双击（file://）即可打开使用，不需要服务器、不需要构建、不需要 node。这是用户实际查阅路径。
2. **零依赖**：无框架、无包管理器、无 CDN 运行时依赖（地图 key 脚本除外，且已有加载失败降级）。
3. **PWA 简单**：Service Worker 只需预缓存 18 个条目，整页即整应用，离线边界清晰。
4. **数据自持**：localStorage / IndexedDB 全在前端，没有后端契约，单文件使「备份 = 拷走一个 HTML + 一次导出」成立。

## 四、四条可选路径对比

### A. 维持现状（推荐）
- 成本：0
- 收益：便携性、零依赖全部保留
- 代价：任务台继续增长；新人（或隔月后的自己）定位函数依赖编辑器搜索

### B. 全量构建化（Vite + 多模块 + 打包回单文件产物）
- 收益：模块化、类型检查、tree-shaking
- 代价：引入 node 工具链与构建步骤；`file://` 双击路径需依赖「构建产物」而非源码，改一行就要重新构建；门禁与守卫需全部重写；PWA 预缓存条目改变
- 判断：**收益不足以覆盖迁移成本**。当前无多人协作、无 npm 依赖诉求。

### C. 外置为同源 ES Module（`<script type="module" src>`）
- 收益：源码层面分文件，易读
- 代价：**`file://` 下 ES module 受 CORS 限制直接不可用**（用户双击打开的 Projects 副本会白屏）；PWA 需额外 precache 每个模块；离线边界从「1 个文件」变成「N 个文件」
- 判断：**直接排除**。这一条会破坏核心使用路径。

### D. 仅外置「非首屏必需的大块数据/模块」，用动态 import + 失败回退
- 收益：任务台首屏可减小（如把海报墙的 1,731 条数据外置成 `媒体数据.js` 按需加载）
- 代价：多一次请求；file:// 下动态 import 同样受 CORS 限制，必须写回退；离线需额外 precache
- 判断：**有条件可行，但当前不需要**。首屏性能已实测可接受（任务台 FCP 1220ms / DCL 1555ms，导航条已静态化避免闪旧版）。

## 五、建议的触发阈值（什么时候才真的该拆）

出现下列任一情况时，再启动路径 D（或局部 C + 服务化部署）：

1. 单文件 > 1.5 MB，或单文件函数数 > 800（任务台当前 822 KB / 590，尚有余量）；
2. 同时维护的页面数 > 10，或出现第二个人参与同一文件改动（冲突率上升）；
3. 首屏关键指标劣化：FCP > 1.8s 或 TTI > 3s（需真机 4G 复测，非本地）；
4. 需要引入真正的依赖（如图表库、富文本编辑器），内联成本高于外置；
5. 单次改动需要人工同步的副本数继续增加（当前 3 处，已接近手工同步的可靠上限）。

在此之前，投入方向应是「继续抽共享块 + 补专项测试」，而不是重构结构。

## 六、当前已识别的具体可优化点（不涉结构重构）

1. **三副本同步靠手工**：`cp` 三条路径重复执行，容易漏。建议在 `check.sh` 增加一条「一键同步三副本」子命令（风险低，收益明确，可列入下一批）。
2. **任务台 590 函数缺少分区索引**：文件内已有层横幅（P1-9 守卫 G11 校验 7 条层横幅），可再补一个「函数名 → 行号」的顶部目录注释块，纯注释不触发 G9。
3. **海报墙数据内联**：1,731 条数据占体积大头，但它同时是「离线可查」的保证，属权衡正确；若未来改为外置，必须保留内联回退。

## 七、诚实披露

- 本文的拆分成本判断基于当前代码与工具链实测（行数/体积/函数数/门禁结构），**未做构建化迁移的 POC 计时**；若未来真要迁移，实际工作量需另行评估。
- 首屏性能数据来自历史实测（FCP 1220ms / DCL 1555ms，本地与线上近似环境），非真机 4G 网络复测。
- 结论是「当前不拆」，不是「永远不拆」；第五节给出了明确的重新评估触发条件。
